# 第 10 章：Ink TUI——UI 只是事件投影

这一章不再讨论 runtime 怎么执行工具，而是讨论客户端怎样观察 runtime。

项目里有两个观察入口：

- CLI 的 `events` / `inspect`：直接读事件日志，离线、可脚本化，适合审计；
- `ui/` 下的 TypeScript Ink TUI：面向真实使用，支持多轮对话和审批，是协议客户端。

TUI 驱动独立的 `mini-harness-server` 后端，走第 9 章的 JSONL 协议。读这章时，把 UI 当成协议客户端，而不是第二个 agent。

## UI 不应该拥有的东西

一个 UI 可以拥有输入框、滚动位置、折叠开关和最后一次看到的 seq。它不应该拥有：

- provider client；
- executor；
- policy 决策；
- event log 的写权限；
- 对 unknown outcome 的猜测；
- 一份自认为权威的 SessionState。

把 UI 进程 kill 掉后，会话仍然在事件日志里。重新 `resume` 或重连，一切从事实恢复。这个性质是判断边界是否正确的简单方法。

## UI 只看到安全投影

打开 `mini-harness-server/src/projection.rs`。durable Event 里的 `tool.requested` 可能包含完整 command、old_text 或工具输入，协议通知不能直接把完整 payload 广播出去。

v2 projection 只保留白名单字段（第 9 章列过完整清单）：`input_summary` / `input_detail` 给审批界面看有界且脱敏的摘要，`result_summary` 只带工具结果元数据（exit code、字节数、hash），stdout / stderr 的原始文本不进投影。完整输入与输出仍留在 event log 里，用 `mini-harness events --format raw` 在本地审计。

客户端因此能显示"正在请求什么"，却拿不到全部原始内容。这是一个信任边界，不是遗漏。

## 事件审计：最小的观察客户端

想看的只是"这个会话发生过什么"，不需要启动服务器：

~~~bash
cargo run -- events <session-id>             # 一行一个事实的摘要
cargo run -- events <session-id> --format raw   # 完整事件（可信环境）
cargo run -- inspect <session-id> --until 7  # 重放到第 7 条时的状态
~~~

`events` 是纯读命令：打开日志（必要时修复半行）、逐条打印、退出。它不经过协议层，也不做投影脱敏（`--format raw`）或只做字段级脱敏（默认格式）——因为它本来就运行在拥有日志的机器上。对比：协议通知为什么必须脱敏？因为客户端可能运行在另一个信任域。

## Ink TUI 的分层结构

打开 ui/src 目录，入口、协议和渲染的分层很清楚，组件则比早期版本多了：

~~~text
main.tsx      入口：解析参数、启动 mini-harness-server、session.create、挂载 React
client.ts     协议客户端：spawn 子进程、按 id 路由响应、转发通知
demoClient.ts 离线演示用的假 client（make tui-demo），不启动后端
ChatApp.tsx   渲染骨架：React state、消息列表、审批提示
Composer.tsx  多行输入与历史；ToolRow / ApprovalPanel 负责工具与审批展示
Markdown.tsx / layout.tsx / editor.ts   渲染、布局与编辑辅助
~~~

main.tsx 每次启动都创建一个新 session，并把 event log 放到临时目录，避免"日志非空"的冲突。它还会检查 stdin 是不是 TTY：不是就报错退出，并提示改用 `mini-harness run`。

## client.ts 怎样路由消息

打开 ui/src/client.ts。它 spawn 出 `mini-harness-server --stdio`（优先找工作区里的构建产物，找不到才退回 PATH），stderr 直接继承给终端，stdout 交给 readline 逐行解析。每条消息只有两种命运：

~~~text
有 id、且 pending 里有它
  └─ response，resolve 对应的 Promise

method = event
  └─ notification，发给 EventEmitter
~~~

如果客户端只读自己的 response，就会漏掉事件；如果把 notification 当 response，等待命令的 Promise 永远不会 resolve。

`request()` 给每条命令分配递增的 id，把 resolve/reject 存进 Map，再写到子进程 stdin。`onEvent()` 返回一个取消订阅函数。整个类不持有任何会话状态——它只负责转发命令、关联响应、转发通知。

## 一次 turn 的交互

用户按下回车后的顺序：

~~~text
turn.start        → 返回 turn_id（输入已持久化）
（后台持续接收 event notification）
turn.wait         → 完成返回最终文本
                  → timeout 返回 turn_pending
                  → 停在审批返回 approval_pending
approval.respond  → 用户按 y/n 后，把决定变成事实
~~~

关键点在审批：`turn.wait` 收到 `approval_pending` 并不代表失败。它对应一条 `tool.requested { requires_approval: true }` 通知；UI 等用户按 y/n，再调 `approval.respond`，然后继续 `turn.wait`。

UI 自己**不执行工具**，也不决定权限。如果 Ink TUI 自己调用模型或 bash，协议边界就被绕开了。

## UI 如何推导生命周期

屏幕上的"运行中 / 等待审批 / 完成"都从事件投影推导，而不是只看某个错误码：

- `tool.requested { requires_approval: true }` 之后没有 `tool.approval.responded` → 等待审批；
- 有执行还没等到 `tool.completed` / `tool.outcome_unknown` → 工具运行中；
- `turn.completed` / `turn.failed` / `turn.cancelled` / `turn.timed_out` → 终态。

UI 不应该看到一次审批请求后永远显示"审批中"；它要处理后续的 `tool.approval.responded`、`tool.completed` 和终态事件。重新连接时，客户端以事件 `seq` 为版本依据补齐缺失通知，而不是相信旧的内存列表。

## 读测试

~~~bash
cd ui && npm run typecheck && npm test
make tui-demo        # 离线播放工具调用、审批和回答
~~~

TUI 的渲染逻辑在 `ui/tests/` 里有组件级测试；协议行为则由第 9 章的服务器测试覆盖。每个检查都在说明同一件事：UI 可以改变显示，但不能改变事实。

## 思考题

1. UI 为什么不能直接读取和解析 event log？（对比 `events` CLI 为什么可以。）
2. 如果通知丢了一条，seq 怎样帮助客户端发现问题？
3. 为什么"等待审批"应该由事件序列推导，而不是只看 `turn.wait` 的错误码？
4. `input_summary` 为什么不能直接等于工具的完整输入？
5. 想显示实时 stdout 增量，需要在协议中增加什么；安全投影边界会怎样变化？
6. UI 重启后，哪些信息可以从事件恢复，哪些纯粹是 UI 本地状态？
